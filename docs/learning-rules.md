# 学习与协作约定

## 1. 总目标

AI 可以帮助执行命令、编写代码和排查错误，但最终目标不是“AI 把项目写完”，而是学习者能够：

- 解释主要业务请求经过了哪些层。
- 独立完成小范围功能修改。
- 根据错误信息找到大致的问题位置。
- 在面试中诚实、清晰地讲述项目取舍。

## 2. 开发原则

1. 优先完成业务闭环，不提前进行性能优化。
2. 每次只引入当前功能必须使用的新知识。
3. 新需求默认进入 `backlog.md`，不能打断当前课程。
4. 第一次实现以简单、正确、可验证为目标。
5. 优化必须由真实问题、测试结果或明确需求驱动。

## 3. 讲解原则

1. 默认学习者是全栈和 AI 应用初学者。
2. 新概念第一次出现时，要用通俗语言解释它解决的问题。
3. 关键代码要解释输入、输出和调用关系，不逐字符讲解语法。
4. 不使用“这个很简单”“显然”之类跳过思考过程的表达。
5. 框架提供的魔法行为必须指出发生时机和作用。

## 4. 每课互动流程

每一课都必须依次经过下面几个阶段：

1. **分析与分工**：AI 先说明本课目标、核心流程和涉及文件，并根据知识难度选择完整样例、可模仿模板或带注释的 `TODO` 骨架。
2. **实现与讲解**：课程按 A、B、C、D 等检查点逐步推进。AI 每次只布置或讲解当前检查点，等待学习者实践并检查结果后，才进入下一个检查点，不得在一次回复中默认完成整课。
3. **检查与整改**：AI 检查实际文件、代码和命令输出，直接修复遗漏或错误，同时说明修改原因、参考答案和易错点；不为同一个普通知识点反复增加问答轮次。
4. **运行与验收**：优先让学习者体验关键命令和页面操作；需要加速时，AI 可以代为执行安全且在授权范围内的实现与检查，但必须如实区分学习者操作和 AI 操作。只有安全风险、破坏性操作或缺少必须由用户完成的外部操作时才暂停。
5. **总结与定档**：补全本课教程和课程总结，核对 Git 差异并创建一次有意义的提交。

课程状态按以下顺序推进：

```text
未开始 → 分析与分工 → 实现与讲解 → 检查整改 → 验收总结 → 已完成
```

只有双方明确确认“本课验收通过”，才能把课程标记为已完成并进入下一课。一次回复结束不代表一课结束，AI 不得自动跳到下一课。

### “继续”与代执行的含义

- 学习者说“继续”，默认只表示进入下一个检查点，不表示授权 AI 一次完成后续所有代码、运行、验收和提交。
- 学习者说“确认”，表示当前要求的命令、页面操作或代码填写已经完成，并且结果符合 AI 给出的验收标准；AI 应据此记录结果并继续，不再机械要求学习者复制完整输出或重复粘贴代码。
- 对已经写入项目的代码，AI 可以在后续检查阶段直接读取实际文件；对只能由学习者观察的终端或页面结果，应接受学习者的“确认”作为完成证据。
- 只有结果与仓库状态矛盾、涉及安全或破坏性操作，或者具体错误输出是继续排错的必要条件时，AI 才在“确认”后追加核实。
- 学习者未填写、不确定或回答错误时，AI 应先提供提示、样例或参考答案；只有学习者明确说“给答案”“帮我实现”或“代我执行”时，AI 才代做对应范围。
- 即使学习者要求 AI 代做某个检查点，也应在完成后停下，说明实际修改和下一步实践，不得据此推断后续检查点也全部交给 AI。
- 普通概念问答不作为阻塞关卡，但核心代码、关键命令和页面操作应优先留给学习者体验。

## 5. 文件与课程记录原则

- `docs/` 只保存稳定的产品需求、协作规则和待办事项。
- `lesson/README.md` 只保存课程路线和完成状态。
- 每节课只维护一个课程文件，不再为计划、笔记、答案和总结分别创建文件。
- 课程文件在教学过程中动态更新，但不记录逐轮问答流水和每次错误尝试。
- 每个阶段只保留目标、核心讲解、实际结果、参考答案和易错点，避免课程文件过长。
- 课程结束后补全“完整教程”和“课程总结”，通过验收后定档；定档前保持“进行中”状态。
- 新建文档前先判断内容能否放进现有文件，避免占位文档和重复进度记录。

### 课程会话命名与衔接

- 每节课使用独立会话，统一命名为 `NoteMind 第XX课：课程主题`，课程编号固定使用两位数字。
- 例如：`NoteMind 第01课：Git与项目起点`、`NoteMind 第02课：FastAPI最小后端`。
- 每课收尾时，AI 必须根据 `lesson/README.md` 给出下一课的准确会话名称；学习者不需要再到其他会话询问命名。
- 下一课只能在当前课程验收通过后开始。新会话仍需先读取项目中的学习规则、课程路线和上一课定档内容。

## 6. 命令记录原则

下面类型的命令必须写入对应课程：

- 初始化项目或依赖
- 创建、升级数据库结构
- 启动前端、后端和数据库
- 执行测试、检查和构建
- Git 阶段性提交
- 部署项目

每条重要命令必须说明：

1. 在哪个目录执行。
2. 为什么执行。
3. 它会修改或启动什么。
4. 如何判断执行成功。

仅用于临时查看目录、搜索代码的诊断命令不必全部记录，避免课程变成流水账。

### AI 代执行命令的透明原则

- AI 可以代为执行安全的只读检查，但不能只给出检查结论；对学习者今后可以复用的检查，必须同时说明执行目录、实际命令、用途和关键输出。
- 启动服务、执行构建、运行测试和页面验收，默认由 AI 给出命令、预期结果和排错提示，再由学习者亲手执行；不能只为加快进度就由 AI 代跑。
- 如果代执行的命令属于本课核心技能，AI 不能以自己的执行代替学习者实践，仍应安排学习者亲手执行或完成等价验收。
- 只有学习者明确要求代执行，或 AI 为定位学习者已经遇到的错误确有必要时，AI 才运行会启动进程、触发环境权限审批或产生大量输出的命令。
- 仅供 AI 临时定位文件、搜索文本或核对内部状态的命令，可以不逐条记录；但其结果如果影响课程决策，必须解释依据。
- 课程文件应区分“AI 检查结果”和“学习者实际操作”，避免把尚未亲手完成的步骤记录为学习者已完成。

### Git 提交原则

- 每课的 `git status`、`git diff`、`git add` 和 `git commit` 默认由学习者亲手执行，作为课程实践的一部分。
- AI 负责给出命令、解释暂存范围、检查差异和建议提交信息，但不能因为学习者说“继续”就代为提交。
- 只有学习者明确说“帮我提交”或明确授权本次 Git 提交时，AI 才可以执行暂存和提交。
- AI 如果误创建了提交，必须如实记录并把后续仍可完成的 Git 实践留给学习者，不得把 AI 提交写成学习者完成。

### 模板、注释与补全原则

- 代码优先写入项目中的真实文件，不在聊天窗口重复输出整份文件；聊天只需说明创建或修改了哪些文件、需要理解和填写的位置、执行命令与验收结果。
- 新知识第一次出现时，AI 优先在真实文件中创建最小完整样例或可运行方向明确的骨架，再安排相似的小修改，避免只给抽象要求。
- 适合学习者补写的代码，应在真实文件中用少量 `TODO(learner)` 注释标出输入、目标和验收结果；不要用大量空白或把机械抄写当练习。
- 学习者完成填写并表示确认后，AI 下一次回复应先读取和审阅实际文件，再直接修复遗漏或错误、解释正确实现，并删除无长期价值的 `TODO(learner)` 教学注释。
- 只有代码很短、用于解释单个概念、文件暂时不可编辑，或学习者明确要求时，才在聊天窗口展示完整代码。
- 模板应保留需要理解的核心部分，不用大量空格或机械抄写制造练习量。
- 学习者可以随时说“给答案”或明确要求跳过、代做当前练习；AI 补全当前范围、说明关键逻辑后，在下一个检查点再次停下。单独说“继续”只推进一个检查点。
- 学习者用“确认”表示代码填写或操作已按验收标准完成时，可以直接进入检查或下一个检查点，不以粘贴全部内容作为推进条件。
- 学习者没有提交概念题答案，不代表没有完成课程。AI 应主动给出参考答案，供学习者按需复习。
- AI 补写的代码仍需经过实际检查和运行验收；加快互动不能省略对成果真实性的验证。

## 7. 每课完成标准

每一课必须包含：

- 明确且有限的学习目标
- 本课需要理解的核心概念
- AI 与学习者的实现分工
- 实际修改过的文件
- 执行过的重要命令
- 可以亲自操作的验收步骤
- 常见错误或实际踩坑
- 复习问题、参考答案和一个小练习
- 对本课完整过程的教程
- 可以快速回顾的课程总结
- 一次有意义的 Git 提交
- 双方明确确认“本课验收通过”
- 已给出下一课的准确会话名称

实际文件、代码、关键命令、运行验收和 Git 提交没有完成时，不能进入下一课；这些成果可以由学习者完成，也可以由 AI 在授权范围内补全。概念题由 AI 直接提供参考答案，学习者按需对照，不要求书面作答。

## 8. 学习检查

每课结束从三个角度自查：

- **复述**：能否用自己的话解释本课的数据流或执行过程？
- **修改**：能否不照抄地完成一个小变化？
- **排错**：关键配置出错时，是否知道从哪里开始检查？

概念问题可以口答、心里作答或直接跳过。AI 应给出参考答案和易错点供学习者自行对照，不因未回答或普通答错而停留；涉及安全或会影响后续操作的误解除外。
