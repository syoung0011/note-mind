## 7. 检查点 B：用户数据与接口契约

本课采用下面的最小用户数据结构：

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `id` | 用户内部标识 | 整数主键，由数据库生成 |
| `username` | 登录用户名 | 非空、唯一、最长 50 个字符 |
| `password_hash` | 密码经过单向哈希后的结果 | 非空、最长 255 个字符 |
| `created_at` | 注册时间 | 非空，由数据库生成带时区时间 |

注册接口契约确定为：

```text
POST /api/auth/register

请求：
{
  "username": "alice",
  "password": "example-password"
}

成功：201 Created
{
  "id": 1,
  "username": "alice",
  "created_at": "2026-10-04T...+00:00"
}
```

输入规则：

- 用户名去除首尾空白后转换为小写，长度为 3～50，只允许小写英文字母、数字和下划线。
- 密码长度为 8～128；密码本身不自动去除空白，因为空白也可能是用户有意设置的密码字符。
- 数据库只保存 `password_hash`，不保存也不记录明文密码。

错误规则：

- 请求格式或字段校验失败：由 FastAPI 返回 `422 Unprocessable Entity`。
- 用户名已经存在：返回 `409 Conflict`。
- 创建成功：返回 `201 Created`。

应用会先查询用户名是否存在，以便尽早返回清楚的错误；数据库仍必须设置唯一约束，处理两个同名注册请求几乎同时到达的情况。数据库约束是最终的数据完整性防线，应用层预检查不能替代它。

注册响应只使用公开响应模型，包含 `id`、`username` 和 `created_at`。无论成功还是失败，都不能返回明文密码或 `password_hash`。

参考答案：`users` 表保存用户标识、规范化用户名、密码哈希和创建时间；注册请求接收用户名与明文密码；响应绝不能包含明文密码或密码哈希。

易错点：密码哈希不是可解密的密文；同一密码的安全哈希通常也不应产生固定的相同字符串；只在代码中检查重复用户名仍可能出现并发竞态，因此还需要数据库唯一约束。

## 9. 检查点 D：密码哈希与注册接口

FastAPI 官方安全教程当前推荐使用带 Argon2 支持的 `pwdlib`，并通过 `PasswordHash.recommended()` 取得推荐配置。Argon2 是专门用于密码存储的慢哈希算法；每个密码还会使用随机盐，因此相同明文通常也会生成不同哈希，增加批量破解成本。

AI 已在 `backend/requirements.txt` 中加入 `pwdlib[argon2]`。学习者先安装并验证依赖；随后将在真实文件中建立安全工具、Pydantic 输入输出模型和注册路由骨架。

学习者安装后，AI 核验到 `pwdlib 0.3.1` 和 `argon2-cffi 25.1.0`，并通过一次临时哈希与校验确认实际使用 `argon2id` 且验证成功。

AI 随后创建了以下骨架：

- `security.py` 使用 `PasswordHash.recommended()` 提供单一的密码哈希入口。
- `schemas/user.py` 定义注册输入和公开响应；用户名先去除首尾空白并转为小写，再检查长度和字符范围。
- `routers/auth.py` 声明 `POST /api/auth/register`，但暂时返回 `501`，核心数据库流程留给学习者完成。
- `main.py` 挂载认证路由，并在 CORS 中允许 `POST`。

`UserPublic` 使用 `from_attributes=True`，因此可以从 SQLAlchemy `User` 对象读取公开字段；响应模型没有 `password_hash`，FastAPI 序列化响应时不会把它返回给客户端。

学习者完成了首次注册流程，AI 审阅时发现并整改了以下问题：

- SQLAlchemy 2 查询应先构造 `select(User)`，再交给 `db.scalar()` 执行；`Session` 没有本课所需的 `db.select(...)` 用法。
- 请求数据来自函数参数实例 `user_in`，不能从 Pydantic 模型类 `UserCreate` 上读取本次请求值。
- `User` 的字段名是 `password_hash`，`hash_password` 是生成这个字段值的函数，不是模型字段。
- `db.add()` 接收新建的 `user` 对象；`db.commit()` 先把事务写入数据库，随后 `db.refresh(user)` 才能重新读取数据库生成的主键和时间。
- 路由声明了 `response_model=UserPublic`，因此直接返回 SQLAlchemy `user` 即可，由 FastAPI 完成公开响应转换；不应写成 `UserPublic(user)`。
- 用户名重复表示请求与当前资源状态冲突，应返回 `409`，而不是表示权限不足的 `403`。

整改后的流程先进行一次友好的查重；提交时仍捕获 `IntegrityError` 并回滚，以处理两个同名请求并发通过预检查的竞态。失败事务必须先 `rollback()`，否则该会话不能继续安全使用。

## 12. 复习问题与参考答案

1. **注册请求经过哪些主要层？** FastAPI 路由接收请求，Pydantic 校验并规范化输入，SQLAlchemy 会话查询和写入，psycopg 与 PostgreSQL 通信，响应模型最后过滤公开字段。
2. **为什么保存密码哈希而不是加密后的密码？** 登录只需要验证输入是否与保存结果匹配，不需要还原明文。专用慢哈希配合随机盐可增加数据库泄露后的破解成本。
3. **为什么应用查重后仍需数据库唯一约束？** 两个请求可能同时查到“尚不存在”；数据库唯一约束才能在最终写入时保证数据完整性。
4. **为什么捕获 `IntegrityError` 后必须回滚？** 提交失败后会话处于失败事务状态，必须 `rollback()` 才能恢复为可继续使用的状态。
5. **为什么直接返回 `User` 不会泄露 `password_hash`？** 路由声明了 `response_model=UserPublic`，FastAPI 只序列化公开模型定义的 `id`、`username` 和 `created_at`。
6. **`409` 和 `422` 有什么区别？** `409` 表示格式正确的请求与现有资源状态冲突；`422` 表示输入没有通过字段规则校验，业务写入逻辑不会执行。

小练习已完成：为 OpenAPI 显式补充注册接口的 `409 Conflict` 响应说明，并确认 `/docs` 能展示该响应。
