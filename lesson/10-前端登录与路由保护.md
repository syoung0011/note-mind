## 1. 本课目标与边界

本课让 Vue 前端具备登录状态，并通过路由守卫阻止未登录用户进入受保护页面。

完成后应当能够解释：

- 登录表单如何按照后端要求提交用户名和密码。
- Access Token 为什么需要保存，以及请求受保护接口时如何携带它。
- 页面刷新后如何用 `/api/auth/me` 恢复并校验登录状态。
- Vue Router 的路由、导航和全局前置守卫分别负责什么。
- 为什么前端路由保护只改善交互，真正的数据权限仍必须由后端保证。

本课范围：

```text
登录页提交凭据
  → 后端签发 Access Token
  → 前端保存 Token
  → 调用 /api/auth/me 获取当前用户
  → 路由守卫根据认证状态放行或跳转
  → 退出登录并清理本地状态
```

本课不实现注册页面和完整笔记 CRUD 页面；笔记页面完整联调属于第 11 课。第一版也不引入 Pinia、刷新令牌、Cookie 会话或复杂权限角色。

## 2. 当前基础

## 5. 检查点 A：认证状态与路由保护

浏览器里的登录状态至少包含两层：

1. Token 是后端签发的访问凭证，前端可以保存并在后续 API 请求中携带。
2. 当前用户是前端从 `/api/auth/me` 得到的用户信息，用于页面展示和判断认证恢复结果。

仅仅在浏览器里存在 Token，不代表它仍然有效。页面刷新时应读取 Token，再调用 `/api/auth/me` 让后端验证；验证失败就清理本地 Token，并把用户带回登录页。

路由守卫在导航发生前运行。公开页面（例如登录页）可以直接进入；标记为需要认证的页面必须等认证恢复完成，再根据是否存在有效用户决定放行还是跳转。

易错点：前端守卫不能代替后端鉴权。用户可以修改浏览器中的 JavaScript 或本地存储，因此所有笔记接口仍必须在后端验证 Token 和数据归属。

进入下一检查点前，请先口头思考：

1. 浏览器中有 Token 时，为什么不能直接认定用户已经登录？
2. 路由守卫和后端鉴权分别解决什么问题？

无需书面提交答案。进入检查点 B 时会先给出参考答案，再安装 Vue Router 并建立最小路由结构。

参考答案：本地存在 Token 只能说明浏览器曾经保存过凭证，Token 是否有效仍需由后端验证；路由守卫负责页面导航体验，后端鉴权负责不可绕过的数据安全边界。

## 6. 检查点 B：安装 Vue Router 并建立路由

学习者在 `frontend` 目录执行：

```powershell
npm install vue-router
```

该命令把 Vue Router 加入运行时依赖，并同步更新 `package.json` 与 `package-lock.json`。实际安装版本为 `5.3.1`。

AI 建立了路由入口、公开登录页和首页组件骨架，并把原有健康检查页面迁移到 `HomeView.vue`。学习者补写了首页的路径、名称、组件和认证标记，四项意图均正确；初次实现把嵌套元信息写成了无效的 `meta.requiresAuth: true`。AI 将其整改为：

```js
meta: { requiresAuth: true }
```

`meta` 是路由配置对象的一个属性，其值仍是一个对象；后续导航守卫通过 `requiresAuth` 标记识别受保护页面。

易错点：访问嵌套属性时可以写 `route.meta.requiresAuth`，但创建对象时必须先用 `meta: {...}` 声明属性和值。

## 7. 检查点 C：登录请求与 Token 保存

前端使用 `URLSearchParams` 构造登录数据，并以 `application/x-www-form-urlencoded` 格式提交到 `POST /api/auth/login`。这种格式与后端的 `OAuth2PasswordRequestForm` 匹配；直接发送 JSON 会导致后端无法从表单中提取字段。

学习者正确把 `formData` 设为 `fetch` 的请求体，但初次使用普通属性赋值写入用户名和密码，其中用户名赋值还位于注释同行，因此不会形成有效的表单字段。AI 整改为：

```js
formData.set('username', username)
formData.set('password', password)
```

请求成功后读取响应中的 `access_token`，以 `notemind_access_token` 为键存入 `localStorage`；请求失败则优先展示后端返回的 `detail`。登录页使用 `@submit.prevent` 阻止浏览器默认刷新，通过 `isSubmitting` 防止提交期间重复操作，成功后按路由名称跳转到首页。

易错点：给 `URLSearchParams` 对象设置普通 JavaScript 属性，不等于向待编码的表单参数中添加字段；必须调用 `set()` 或 `append()`。

## 8. 检查点 D：恢复当前用户与退出登录

认证模块增加了 `currentUser` 和 `isAuthReady` 两个响应式状态。`restoreAuth()` 先读取本地 Token：没有 Token 时直接结束恢复；存在 Token 时调用 `GET /api/auth/me`，由后端验证签名、有效期和用户是否存在。

受保护请求使用标准 Bearer 请求头：

```js
headers: {
  Authorization: `Bearer ${token}`,
}
```

学习者初次把请求头写成了 `"Authorization: Bearer": token`，正确理解了需要携带 Token，但混淆了请求头名称与请求头值。AI 将键整改为 `Authorization`，将值整改为 `Bearer`、空格和实际 Token 的组合。

验证成功后，响应中的用户对象写入 `currentUser`；验证失败或网络异常时清除本地 Token 和内存用户，避免继续保留无法确认的登录状态。`finally` 确保无论成功失败，认证恢复最终都会标记为完成。

退出登录会删除 `localStorage` 中的 Token、清空 `currentUser`，再跳转到登录页。当前后端使用无状态 JWT，没有需要调用的服务端退出接口。

易错点：HTTP 请求头对象的键是纯名称 `Authorization`，冒号是 HTTP 文本格式中的分隔符，不属于名称；`Bearer` 属于请求头的值，而且后面必须有一个空格。

## 9. 检查点 E：路由守卫与页面跳转

全局前置守卫在每次导航确认前运行。首次导航时，如果 `isAuthReady` 仍为 `false`，守卫先等待 `restoreAuth()`，避免页面刷新后在后端尚未验证 Token 时误判为未登录。

认证恢复完成后，守卫按顺序判断：

```text
目标路由需要认证且没有当前用户 → 跳转登录页
目标是登录页且已有当前用户     → 跳转首页
其他情况                       → 正常放行
```

学习者正确写出了 `to.meta.requiresAuth && !currentUser.value` 条件和登录页路由位置对象，但条件紧跟在单行注释后面，导致整段条件被 JavaScript 忽略。AI 将条件移动到独立代码行、统一格式并删除教学注释。

守卫检查的是后端验证后得到的 `currentUser`，而不是只检查 `localStorage` 中是否存在 Token。这样过期、伪造或对应用户不存在的 Token 都不会被当作有效登录状态。

易错点：`//` 会注释从它开始直到换行的全部内容；在注释同行追加代码时，即使代码文字正确也不会执行，并可能使后续花括号失去配对。

## 10. 检查点 F：构建与运行验收

学习者在 `frontend` 目录执行：

```powershell
npm run build
```

该命令让 Vite 编译 Vue 组件、解析模块导入并生成生产构建。学习者确认构建成功，没有出现 `error during build`；生成的 `dist/` 已由 Git 忽略。

学习者随后分别在 `backend` 目录执行 `fastapi dev app/main.py`，在 `frontend` 目录执行 `npm run dev`，启动后端与前端开发服务器。首次登录时页面一直显示“正在登录”，前后端暂时没有完成日志。实际原因是 PostgreSQL 容器没有启动。

故障链路如下：

```text
提交登录表单
  → FastAPI 登录接口开始查询用户
  → SQLAlchemy 首次真正请求数据库连接
  → PostgreSQL 容器未启动
  → 数据库连接等待超时
  → HTTP 响应尚未完成
  → 前端 await fetch() 持续等待
  → finally 尚未执行，isSubmitting 一直为 true
```

后端能够启动且 `/health` 正常，是因为 SQLAlchemy 创建 Engine 时通常不会立即连接数据库，而登录查询才真正需要连接；`/health` 本身也不访问数据库。Uvicorn 的访问日志通常在请求完成后输出，因此等待数据库连接期间可能暂时看不到该请求的完成日志。

排错经验：后端进程启动不等于数据库可用，健康接口正常也不等于数据库业务接口正常；当前端持续加载时，应检查浏览器 Network 中是否存在 pending 请求，并继续检查该请求依赖的数据库等下游服务。启动 PostgreSQL 容器后，学习者重新登录成功。

学习者完成并确认以下浏览器验收：

- 正确凭据登录成功，首页显示当前用户名。
- 刷新首页后，通过 `/api/auth/me` 恢复登录状态。
- 已登录用户访问 `/login` 时自动返回首页。
- 退出登录后进入登录页，再直接访问首页会被守卫拦截。
- 错误密码显示后端错误信息，提交按钮恢复可用。
- 手动篡改本地 Token 后刷新，`/api/auth/me` 返回 `401`，前端清除无效 Token 并跳转登录页。

### 小修改

学习者为登录页补充与后端账号约束一致的浏览器长度校验：用户名为 3～50 个字符，密码为 8～128 个字符。页面验证确认长度不足时浏览器阻止提交，满足约束后仍可正常登录。

## 11. 复习问题与参考答案

1. **为什么本地存在 Token 仍要请求 `/api/auth/me`？** Token 可能过期、伪造，或者对应用户已不存在；只有后端验证后才能确认登录有效，并返回可信的当前用户信息。
2. **为什么登录请求不能直接发送 JSON？** 当前后端使用 `OAuth2PasswordRequestForm`，要求 `application/x-www-form-urlencoded` 表单编码。
3. **Bearer 请求头怎样组成？** 请求头名称是 `Authorization`，值是 `Bearer`、一个空格和 Token，即 `Authorization: Bearer <token>`。
4. **为什么守卫要等待认证恢复？** 页面刷新后内存中的 `currentUser` 初始为空；如果不等待 `/api/auth/me`，会把有效登录误判为未登录。
5. **前端路由守卫能否保护笔记数据？** 不能。守卫只能控制正常页面导航，真正的数据访问仍必须由后端鉴权和用户数据过滤保护。
6. **数据库未启动时为什么 FastAPI 和 `/health` 仍可能正常？** SQLAlchemy 通常延迟到第一次查询才建立连接，而当前 `/health` 不访问数据库。

## 13. 完整教程

前端先通过 Vue Router 把 `/login` 映射到公开登录页，把 `/` 映射到带有 `meta.requiresAuth` 标记的首页。根组件只负责渲染 `RouterView`，具体页面由当前路由决定。

登录页使用 `v-model` 收集用户名和密码，使用 `URLSearchParams` 生成 OAuth2 表单请求。后端验证成功后返回 Access Token，前端将其保存到 `localStorage`，随后用标准 Bearer 请求头调用 `/api/auth/me`。只有这个请求成功后，响应中的用户才写入 `currentUser`。

页面刷新时，内存状态会重新初始化，但本地 Token 仍存在。全局前置守卫在首次导航时等待 `restoreAuth()`：有效 Token 恢复用户，无效 Token 被清除。认证恢复完成后，守卫根据路由元信息和 `currentUser` 决定放行或跳转。退出登录则清除 Token 与用户状态并返回登录页。

本课通过构建和真实浏览器操作验证了登录、刷新恢复、退出、错误密码、未登录访问受保护页面以及无效 Token。期间 PostgreSQL 容器未启动造成请求持续等待，进一步验证了前端、后端、数据库三层调用链及 pending 请求的排查方法。
