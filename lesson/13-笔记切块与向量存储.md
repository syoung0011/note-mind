```text

```

## 2. 实现方案

第一版采用容易运行和理解的实现：

- 按字符长度切块，并保留少量重叠，避免信息刚好被边界截断。
- 每个片段保存 `note_id`、`user_id`、`chunk_index`、原文和向量。
- 向量先使用 PostgreSQL 数组字段保存。
- 第 14 课在当前用户的小规模片段中用 Python 计算余弦相似度。
- 暂不引入 pgvector、近似最近邻索引或异步任务队列；数据规模证明有需要时再优化。

采用数组而不是 pgvector 不会改变 RAG 的核心流程。它只表示第一版把“向量存储”和“高性能向量检索”分开处理，降低本地环境搭建成本。

## 5. 检查点 A：索引路径与数据一致性

当前 `notes` 表只保存完整标题和正文。全文适合编辑和展示，但不适合直接作为检索单位：内容过长时会混入多个主题，也会占用更多模型上下文。因此需要派生出 `note_chunks`。

```text
notes（一篇可编辑的完整笔记）
  └─ note_chunks（多个可检索的片段）
       ├─ chunk_index：片段在原笔记中的顺序
       ├─ content：送给模型和展示引用的原文
       └─ embedding：用于相似度比较的数字数组
```

`note_chunks` 是由笔记正文生成的派生数据，不是另一份由用户独立编辑的内容。三种写操作必须保持一致：

- 创建笔记：保存笔记并生成全部片段。
- 更新笔记：旧片段失效，应删除后根据新正文整体重建。
- 删除笔记：对应片段随笔记一起删除。

为了避免用户看到新正文、检索却仍命中旧片段，笔记写入与片段重建应尽量放在同一个数据库事务中。Embedding 是外部调用，可能失败；本课会在后续检查点明确第一版的失败处理方式。

### 当前思考题

先口头思考即可，不要求发送书面答案：

1. 为什么更新正文后不能只追加新片段？
2. `chunk_index` 不参与相似度计算，为什么仍然需要保存？
3. `user_id` 已经能通过 `note_id` 间接找到，为什么片段表仍值得保存它？
4. 为什么本课暂不安装 pgvector 仍然可以完成“向量存储”？

进入检查点 B 时，AI 会先给出参考答案，再在真实文件中创建切块函数骨架。

### 检查点 A 参考答案

1. 更新后只追加会同时保留新旧内容，检索可能命中过期片段；第一版整体删除并重建更容易保证一致。
2. `chunk_index` 可以恢复片段在原文中的顺序，便于调试、展示相邻上下文以及稳定地重建索引。
3. 片段直接保存 `user_id` 后，检索可以在查询层先限定当前用户，不必依赖应用代码先关联笔记再过滤；这是清晰的数据隔离边界。它也意味着创建片段时必须保证 `user_id` 与所属笔记一致。
4. “向量存储”要求能够持久保存并读取数字向量；pgvector 提供的是专用向量类型、距离运算符和索引能力，并不是保存向量的唯一方式。当前规模用 PostgreSQL 数组加 Python 相似度计算即可跑通流程。

## 6. 检查点 B：实现纯文本切块

切块函数保持为纯 Python：输入正文、块大小和重叠长度，输出按原文顺序排列的字符串列表。它不访问数据库，也不调用模型，因此可以独立验证。

本课采用固定长度滑动窗口：

```text
chunk_size = 8, overlap = 2

第 1 块：[0, 8)
第 2 块：[6, 14)
                 ↑ 下一块从“上一块结束位置 - overlap”开始
```

重叠能保留边界附近的上下文，但重叠必须小于块大小，否则窗口无法向前移动。函数需要检查：

- `chunk_size` 必须大于 0。
- `overlap` 必须大于等于 0 且小于 `chunk_size`。
- 只有空白的正文返回空列表。
- 到达原文末尾后必须停止，避免产生重复尾块或死循环。

AI 已创建：

- `backend/app/services/chunking.py`：参数校验和函数骨架。
- `backend/examples/chunking_demo.py`：三个无需数据库的断言，用于验证短文本、重叠和空白正文。

学习者需要补全 `split_text()` 中的 `TODO(learner)`：使用滑动窗口依次取出片段，去掉片段两端空白，把非空片段加入列表，并在末块后停止。

完成后，在 `backend` 目录执行：

```powershell

```

该命令只运行本地 Python 切块示例，不启动 FastAPI、不连接数据库，也不访问网络。使用 `-m` 可以让 `backend` 保持为模块导入根目录，使示例能够导入同级的 `app` 包。成功标志是显示 `Chunking demo passed.`，且没有断言错误。

### 检查与整改结果

学习者尝试用 `while` 循环切片，并正确认识到需要维护起始位置；但最初把 `end` 设为 `text[-1]`，得到的是最后一个字符而不是文本长度，整数 `start` 无法与字符串比较。同时每轮直接增加 `chunk_size`，没有保留重叠，教学 TODO 也仍未删除。

AI 将循环修正为：用 `len(text)` 判断边界，以 `min(start + chunk_size, len(text))` 计算末端，整理并保存非空窗口；不是末块时再令 `start = end - overlap`。首次复验还发现直接运行 `python examples/chunking_demo.py` 时导入根目录落在 `examples`，无法找到同级的 `app` 包，因此命令改为 `python -m examples.chunking_demo`。修复后由 AI 运行验证脚本，三个断言全部通过。学习者此前报告脚本成功，但仓库代码与该结果矛盾，因此课程只记录学习者完成了尝试，最终成功结果来自 AI 整改后的复验。

易错点：`text[-1]` 是最后一个字符；`len(text)` 才是文本长度。重叠窗口的步长实际是 `chunk_size - overlap`，不能仍按完整块大小前进。

## 7. 检查点 C：`NoteChunk` 模型与迁移

`NoteChunk` 模型把每个可检索片段保存为独立记录：

- `note_id`：片段属于哪篇笔记。
- `user_id`：检索时直接限定当前用户的数据范围。
- `chunk_index`：片段在笔记中的稳定顺序，从 0 开始。
- `content`：生成向量时使用的原文，也是后续引用展示的依据。
- `embedding`：PostgreSQL 浮点数组，保存 Embedding 模型返回的向量。
- `created_at`：记录该片段何时生成。

## 9. 检查点 E：接入笔记写入事务

- 删除：无需手工调用索引服务；迁移中的 `ON DELETE CASCADE` 会在删除笔记时由 PostgreSQL 清理片段。

## 13. 复习问题与参考答案

1. **为什么需要重叠切块？** 边界可能截断一句话或一个知识点；少量重叠让相邻片段都保留边界上下文。重叠越大，重复存储和模型调用成本也越高。
2. **为什么 `overlap` 必须小于 `chunk_size`？** 下一块起点是 `end - overlap`；两者相等时窗口无法前进，可能造成死循环。
3. **`flush()` 和 `commit()` 有什么区别？** `flush()` 把当前变更发送到数据库并可取得主键，但事务仍可回滚；`commit()` 才最终提交整个事务。
4. **更新为什么整体重建片段？** 旧片段的位置和内容可能全部失效；第一版删除后重建比计算增量差异更容易保证正确性。
5. **为什么 Embedding 响应要按 `index` 排序？** 数据库记录必须与原输入片段一一对应；不能假设响应数组天然保持顺序。
6. **为什么索引服务不自行提交？** 路由需要把笔记变更和索引变更放进同一个事务，使它们一起成功或回滚。
7. **删除为何不手工清理片段？** `note_id` 外键配置了 `ON DELETE CASCADE`，数据库会在删除笔记时原子地清理所属片段。
8. **为何当前不用 pgvector？** MVP 数据量小，可以先用 PostgreSQL 数组保存、下一课在 Python 中计算相似度；专用向量索引应由真实规模和性能问题驱动。

## 14. 完整教程与阶段总结

本课从完整笔记不能直接成为理想检索单位出发，先实现带重叠的固定字符窗口，并用纯 Python 示例验证顺序、重叠、空白正文和非法参数。随后建立 `note_chunks` 表，用外键、唯一约束和索引表达片段归属、顺序与生命周期；向量暂存为 PostgreSQL 浮点数组。

Embedding 层使用阿里云百炼 `text-embedding-v4` 的 OpenAI 兼容接口，输出 1024 维向量。服务按供应商单批上限分组调用，再依据响应 `index` 恢复输入顺序。索引服务把片段和向量配对，先删除旧片段再构造新片段，但把提交权留给路由。

创建笔记时先 `flush()` 获得主键，再生成索引并统一提交；更新时重建索引后统一提交；删除时依靠数据库级联约束。端到端验收确认创建、更新和删除时片段与笔记保持同步，同时检查脚本不暴露正文、完整向量和密钥。
