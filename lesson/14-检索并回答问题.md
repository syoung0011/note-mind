## 2. 核心流程

```text
登录用户的问题
  → 为问题生成 Embedding
  → 查询当前用户的 note_chunks
  → 计算问题向量与片段向量的余弦相似度
  → 按分数降序选择 Top-K
  → 把命中片段组装成上下文
  → 要求 LLM 只根据上下文回答
  → POST /api/chat 返回回答
```

数据库在当前 MVP 中保存 PostgreSQL 浮点数组，候选片段由数据库按 `user_id` 过滤，再由 Python 计算余弦相似度。这样可以先跑通 RAG 核心流程；数据规模确实增大后，再考虑 pgvector 等数据库内向量检索方案。

## 5. 检查点 A：先理解检索与回答的职责

检索和回答是两个不同阶段：检索负责从用户自己的片段中找出最相关的事实材料；LLM 负责阅读这些材料并组织自然语言答案。LLM 不应负责决定用户能访问哪些数据，因此 `user_id` 过滤必须发生在数据库查询阶段，而不是生成提示词以后。

Top-K 表示按相似度排序后最多取前 K 个片段。K 太小可能遗漏上下文，太大则会混入无关内容并增加模型输入成本。本课先使用固定且较小的 K 跑通链路，第 15 课再结合阈值和评测调整质量。

进入检查点 B 前，先口头思考：

1. 为什么不能先读取所有用户的片段，算完相似度后再按 `user_id` 过滤？
2. 为什么检索结果不能只保存相似度分数，还必须保留原片段对象？
3. 如果数据库中没有当前用户的任何片段，检索函数最自然的返回值是什么？

这些问题不要求书面作答。进入下一检查点时，AI 会给出参考答案并创建检索服务骨架。

### 检查点 A 参考答案

1. 必须先由数据库按 `user_id` 限定候选范围。如果先读取所有人的片段，其他用户的数据已经越过了业务隔离边界；即使最终不返回，也增加了泄露、日志暴露和代码遗漏过滤的风险。
2. 相似度只说明“有多相关”，不能提供回答所需的原文，也无法追溯片段所属笔记。检索结果必须同时保留片段对象和分数。
3. 最自然的结果是空列表。它表示检索过程正常完成但没有候选数据，调用方可以据此决定如何回应，而不应把正常的“无数据”当成系统异常。

易错点：身份隔离属于数据库查询职责，不能寄希望于提示词要求模型忽略其他用户的数据；提示词不是权限系统。

### 学习者实现评阅与整改

学习者正确完成了候选片段遍历，并对问题向量和每个片段向量调用余弦相似度函数。原实现还有三个问题：

- `NoteChunk` 是 SQLAlchemy 模型对象，不是映射，不能使用 `{**chunk, "score": score}` 展开。
- 函数声明返回 `list[RetrievedChunk]`，实际却构造了字典，类型和后续属性访问不一致。

AI 保留循环评分思路，将每项改为 `RetrievedChunk(chunk=chunk, score=score)`，并用 `reverse=True` 降序排列。排序逻辑提取为纯函数 `rank_chunks()`，便于在不连接数据库、不调用 Embedding API 的情况下验证。

- `chat_model_demo`：真实访问聊天模型，会产生少量 API 用量。
- `chat_route_demo`：用替换函数验证当前用户 ID、回答分支和空结果分支。

## 13. 复习问题与参考答案

1. **为什么先按 `user_id` 查询，再计算相似度？** 数据权限必须在候选数据进入应用检索逻辑前生效；提示词和事后过滤都不能替代数据库查询边界。
2. **余弦相似度比较的是什么？** 它比较两个向量方向的接近程度，不主要受向量长度影响；方向越接近，通常代表语义越相关。
3. **Top-K 解决什么问题？** 它只保留分数最高的有限数量片段，控制上下文噪声和模型输入成本，但它本身不能判断最高分是否已经足够相关。
4. **为什么检索结果同时保存片段和分数？** 分数用于排序和后续阈值判断，片段正文用于回答，片段身份则用于后续引用追踪。
5. **系统提示词为什么不是权限系统？** 模型可能误解或忽略文本指令；权限必须由可靠的认证和数据库过滤执行，模型只能接触已授权内容。
6. **为什么上下文要有编号和分隔？** 清晰边界可防止片段粘连，保留排名，并为下一课把回答与引用片段对应起来提供结构。
7. **为什么无候选片段时不调用聊天模型？** 模型没有可依据的资料，调用只会增加成本和生成臆测的风险。
8. **本课为什么还不能完整保证“资料不足时拒答”？** 只要用户存在片段，当前实现就会取 Top-K，即使最高分很低；还需要第 15 课的阈值、引用和测试问题集来判断资料是否足够。

## 14. 完整教程与课程总结

本课把第 13 课保存的向量片段接入真实问答链路。请求首先通过 Bearer Token 得到当前用户；检索服务只查询该用户的 `note_chunks`，为问题生成同维度 Embedding，在 Python 中计算余弦相似度，按分数降序返回前三个候选。当前数据规模较小，因此没有提前引入 pgvector。

回答服务把检索结果转换为带编号和空行分隔的文本上下文，通过系统提示词要求模型只依据笔记内容回答，再使用现有百炼 OpenAI 兼容接口调用 `qwen-plus`。聊天路由负责把认证、检索和回答串联起来，并在用户完全没有片段时避免调用模型。

学习者在实现中正确完成了相似度循环、检索调用、用户 ID 传递和空结果分支。整改内容包括：将 SQLAlchemy 对象正确包装为 `RetrievedChunk`、改为相似度降序、正确读取片段正文并返回上下文，以及把错误的 `raise` 模型回答改为 `ChatResponse` 返回。
