## 5. 检查点 A：测试层次与优先级

自动化测试的价值不是追求文件数量或覆盖率数字，而是在代码变化后快速回答：“最重要的行为有没有被破坏？”

- **单元测试**：隔离数据库、网络和外部模型，检查一个函数的输入与输出。例如文本切块、引用整理和拒答判断。
- **接口集成测试**：通过 FastAPI 接口发起真实请求，检查路由、认证、数据库和响应结构能否协作。例如注册后登录、未登录不能访问笔记、用户只能查看自己的笔记。
- **端到端验收**：从浏览器或已部署入口走完整流程，确认前端、后端、数据库和网络配置共同可用。本课保留少量关键人工验收，不立即引入浏览器自动化框架。

当前 MVP 的最小保护网优先覆盖：

1. 注册、登录与受保护接口，避免身份认证失效。
2. 笔记 CRUD 与用户数据隔离，避免越权读取或修改。
3. RAG 中不依赖真实模型网络的确定性逻辑，避免测试被费用、网络和模型波动影响。
4. 前端生产构建、Compose 配置检查和线上核心流程，避免“代码能测但产品不能运行”。

易错点：自动化测试默认不应调用真实付费模型；数据库测试也不能污染开发或部署数据库。后续会为测试准备可重复创建和清理的隔离环境。

### 学习者任务

### 参考答案

`/health` 只证明 FastAPI 进程能响应，几乎不经过认证、数据库和数据权限。完整业务场景会同时覆盖请求校验、密码哈希、JWT、依赖注入、数据库写入以及按 `user_id` 隔离查询；其中数据越权会直接泄露用户隐私，因此它比单纯的存活检查风险更高、回归价值更大。

## 6. 检查点 B：测试环境与数据库隔离

本检查点新增独立的开发依赖文件 `backend/requirements-dev.txt`。它先通过 `-r requirements.txt` 复用运行依赖，再增加 `pytest` 和 FastAPI `TestClient` 所需的 `httpx`；生产镜像仍安装原来的 `requirements.txt`，不会把测试工具打进运行镜像。

`backend/tests/conftest.py` 提供可复用的 `client` fixture：

1. 使用 `StaticPool` 保持同一个内存 SQLite 数据库连接。
2. 只为接口测试创建 `users` 和 `notes` 表，避开 SQLite 不支持的 PostgreSQL `ARRAY` 字段。
3. 通过 `app.dependency_overrides` 将应用的 `get_db` 替换为测试会话。
4. 将笔记索引替换为空操作，避免请求真实 Embedding 服务。
5. 每个测试结束后清除依赖覆盖并删除测试表，避免测试之间相互污染。

`backend/tests/test_health.py` 是最小示例，用来验证测试收集、TestClient 和断言链路能够正常工作。它不是本课最重要的业务保护；后续认证与数据隔离测试才是核心。

易错点：测试数据库隔离不等于把开发数据库地址复制一遍。任何测试都不应对 `backend/.env` 指向的真实数据库执行清表或删库操作。

### Render 架构与适配

Render 部署拆分为三个资源：

```text
浏览器 → Render Static Site → Render Docker Web Service → Render PostgreSQL
```

本地 Compose 通过 Nginx 同源代理 `/api`，而 Render 静态站点和后端拥有不同域名，因此进行了以下兼容改造：

- `frontend/src/services/api.js` 从 `VITE_API_BASE_URL` 读取公开后端地址；变量留空时仍使用本地同源 `/api`。
- 认证和笔记请求统一通过 `apiUrl()` 生成地址，避免在各文件中重复判断环境。
- 后端通过 `CORS_ORIGINS` 接受允许访问 API 的前端来源，本地默认来源保持不变。
- 后端将 Render 提供的 `postgresql://` 连接串转换为 SQLAlchemy 使用当前 psycopg 驱动所需的 `postgresql+psycopg://`。
- 后端容器优先监听平台注入的 `PORT`，本地没有该变量时仍使用 `8000`。
- 根目录 `render.yaml` 声明新加坡区域的 Docker 后端、静态前端和 PostgreSQL，并用 `sync: false` 标记必须在控制台填写的模型密钥。

真实 `.env`、数据库密码、JWT 密钥和模型 API Key 均未被 Git 跟踪。验证结果：后端 `4 passed`、前端生产构建成功、数据库 URL 与 CORS 配置转换检查通过、Compose 配置检查通过、`git diff --check` 无错误。

### Docker 安装与镜像网络整改

服务器访问 Docker 官方 APT 仓库时出现 TLS 连接被重置，导致 `docker-ce` 等包没有候选版本；改用腾讯云 Ubuntu 镜像源后，成功安装 Docker 29.1.3、Compose 2.40.3 和 Buildx 0.30.1。

第一次运行 `hello-world` 时，服务器直连 `registry-1.docker.io:443` 超时。学习者随后在 `/etc/docker/daemon.json` 配置腾讯云 VPC 内网镜像加速地址 `https://mirror.ccs.tencentyun.com`，校验 JSON 并重启 Docker。`docker info` 显示镜像地址生效，`hello-world` 成功拉取、运行并自动删除，证明 Docker 客户端、守护进程、镜像下载和容器执行链路全部正常。

易错点：APT 软件包镜像与 Docker 容器镜像是两套下载链路；能够通过腾讯云 APT 源安装 Docker，不代表能够直接访问 Docker Hub。排错时应分别验证软件包仓库和容器镜像仓库。

### 容器构建依赖源整改

服务器克隆提交 `2bb2bf4` 后创建了权限为 `600` 的根目录和后端 `.env`。Compose 配置校验退出码为 0；编辑器意外生成的 `.env.save` 包含真实配置且未被忽略，学习者按要求立即删除。项目 `.gitignore` 随后增加 `.env.*` 并通过 `!.env.example` 保留配置模板，防止环境文件备份被误提交。

第一次执行 `docker compose up --build -d` 时，PostgreSQL 和三个基础镜像能够通过腾讯云 Docker 镜像加速下载，但后端镜像内的 `pip install` 无法从默认 PyPI 获得 SQLAlchemy，约一分钟后报告 `No matching distribution found`。这不是版本约束错误，而是容器构建阶段访问境外 Python 软件源失败；前端构建被 Compose 联动取消，尚不能据此判断 npm 是否可访问。

为保持跨环境兼容，后端 Dockerfile 增加 `PIP_INDEX_URL` 构建参数，前端 Dockerfile 增加 `NPM_REGISTRY` 构建参数；Compose 可从根目录 `.env` 注入地址，未设置时仍默认使用 PyPI 与 npm 官方源，因此本地和 Render 行为保持不变。腾讯云部署使用其统一镜像域名下的 PyPI 和 npm 缓存。

学习者创建并推送提交 `2f16d94 fix: support mirrored container builds`，服务器快进拉取后在根目录 `.env` 注入腾讯云 PyPI 与 npm 地址。第二次构建成功，PostgreSQL 与后端均达到 healthy，前端容器正常运行。学习者将前端映射改为公网标准端口 80；服务器内部请求前端返回生产 HTML，请求后端 `/health` 返回预期 JSON。

公网开放前检查发现后端仍以 `0.0.0.0:8000` 发布到宿主机。Nginx 容器通过 Compose 内部网络访问 `backend:8000`，无需让 API 端口对公网网卡监听；因此 Compose 将后端宿主机绑定收紧为 `127.0.0.1:8000:8000`。公网只需开放 Nginx 的 80/443，PostgreSQL 继续不发布宿主机端口。

学习者创建并推送安全提交，服务器拉取后重建后端。最终容器状态为：PostgreSQL healthy 且只在 Compose 网络暴露 5432；后端 healthy 且宿主机只监听 `127.0.0.1:8000`；前端监听公网标准端口 80。服务器内部前端 HTML 和 API 健康检查均成功，AI 从外部请求公网 IP 的前端得到 HTTP 200，请求 Nginx 代理的未认证 `/api/auth/me` 得到预期 HTTP 401，证明腾讯云安全组、Nginx 和内部 API 代理共同生效。

学习者没有域名。虽然 Let’s Encrypt 已可签发约六天有效的公网 IP 证书，但当前 Certbot 仍需额外手工配置容器 Nginx、证书挂载、频繁自动续期和重载。本课不为第二演示环境引入这套运维复杂度：Render 作为 HTTPS 公开演示入口；腾讯云完成 Compose 与公网连通验收，但 HTTP 入口不使用真实或复用密码。

### 关键技术取舍

- 使用单体 FastAPI、Vue 和 PostgreSQL 完成 MVP，不提前引入微服务、任务队列或 Kubernetes。
- 笔记保存时同步建立索引，流程直观且容易验收；代价是模型服务失败会让保存请求失败，后续可以改为可重试的异步任务。
- 接口测试使用隔离 SQLite，并替换真实 Embedding 调用，保证快速稳定且无费用；代价是部署环境的模型地址和网络必须另做集成验收。
- Render 降低基础设施维护成本但免费资源有休眠和数据库过期限制；腾讯云 Compose 更可控，但需要自行处理镜像、端口、TLS、更新和备份。
- 服务器只公开 Nginx，API 仅绑定回环地址，数据库仅存在于容器网络，减少不必要的攻击面。

### 复习问题与参考答案

1. **为什么测试通过仍会在线上创建笔记失败？** 测试替换了真实 Embedding 调用，而线上模型 URL 混入换行；自动化测试和部署验收保护的是不同边界。
2. **为什么 Docker 镜像加速不能解决 pip 失败？** Docker Hub、PyPI 和 npm 是三套独立下载链路，需要分别配置。
3. **为什么公网不开放 8000 和 5432？** 浏览器统一访问 Nginx，Nginx 通过内部网络访问 API，API 再访问数据库；直接暴露内部服务只会增加攻击面。
4. **Render 和腾讯云分别由谁负责更多运维？** Render 管理运行平台、TLS 和托管数据库；腾讯云只提供服务器，系统、Docker、网络、TLS、备份和更新由项目方负责。
5. **当前最值得继续改进的可靠性问题是什么？** 将同步索引改为有状态、可重试的异步流程，避免模型暂时不可用时阻止笔记保存。
