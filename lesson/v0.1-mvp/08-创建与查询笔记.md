## 1. 本课目标与边界

本课完成笔记数据的第一条后端业务闭环：已登录用户可以创建笔记、查看自己的笔记列表，并查看自己某一篇笔记的详情。

需要理解：

- `users` 与 `notes` 的一对多关系，以及外键解决的问题。
- 请求体、数据库模型和响应模型各自负责什么。
- 路由如何通过 `get_current_user` 获得当前用户。
- 查询为什么必须同时包含笔记条件和当前用户条件。
- 为什么“不存在”和“不属于当前用户”统一返回 `404`。

本课范围：

```text
POST /api/notes       创建当前用户的笔记
GET  /api/notes       查询当前用户的笔记列表
GET  /api/notes/{id}  查询当前用户的一篇笔记
```

本课不实现编辑、删除、前端笔记页面、分页、搜索、标签、Markdown 编辑器、笔记切块和向量索引。

## 2. 核心流程

```text
Bearer Token
  → get_current_user 验证身份并取得 User
  → notes 路由处理输入
  → SQLAlchemy 只写入或查询 current_user.id 对应的数据
  → Pydantic 响应模型过滤并序列化公开字段
```

计划中的数据关系：一个用户可以拥有多篇笔记，每篇笔记只能属于一个用户。

## 5. 检查点 A：设计笔记数据和接口边界

第一版 `notes` 表计划保存以下信息：

- `id`：笔记主键。
- `user_id`：所属用户的外键，也是所有笔记查询的数据隔离边界。
- `title`：笔记标题，限制合理长度。
- `content`：笔记正文，使用可保存长文本的字段。
- `created_at`：创建时间，由数据库生成。
- `updated_at`：最后更新时间，由数据库生成并在更新时维护，为第 9 课做准备。

接口约定：创建成功返回 `201`；列表只返回当前用户的数据；详情不存在或属于其他用户时统一返回 `404`，避免泄露某个笔记 ID 是否真实存在。

开始编码前，学习者先用自己的话说明：为什么 `notes` 表必须保存 `user_id`，以及为什么查看详情时不能只按笔记 `id` 查询。

易错点：JWT 中的用户 ID 只用来确认请求者身份；真正的数据隔离仍要落实到每一条数据库查询条件中。

学习者已说明：笔记归属于用户，查询笔记时也必须核对笔记是否属于当前用户。这个理解正确。进一步的安全边界是：查询详情必须同时限制笔记 `id` 和当前用户的 `user_id`，并将“笔记不存在”和“属于其他用户”统一处理为 `404`，避免泄露资源是否存在。

- `id`：整数主键。
- `user_id`：不可为空的整数外键，指向 `users.id`，并建立索引。
- `title`：不可为空的 `String(200)`。
- `content`：不可为空的 `Text`。
- `created_at`：带时区的时间，使用数据库默认值 `func.now()`，不可为空。
- `updated_at`：带时区的时间，创建时使用 `func.now()`，更新时使用 `onupdate=func.now()`，不可为空。

字段使用 SQLAlchemy 2.0 的 `Mapped[...]` 和 `mapped_column(...)` 写法，与现有 `User` 模型保持一致。外键保证 `notes.user_id` 引用真实用户；索引则为以后频繁按用户查询笔记提供基础。

## 7. 检查点 C：定义笔记请求与响应模型

本检查点区分两种接口数据：

- `NoteCreate` 是创建笔记的请求体，只允许客户端提交 `title` 和 `content`。

请求体不能包含 `user_id`。笔记所有者必须来自已经过验证的 `current_user.id`；如果允许客户端自行提交所有者 ID，攻击者就可能把数据写到其他用户名下。

## 9. 检查点 E：实现笔记列表与详情查询

AI 已在 `notes.py` 增加列表和详情接口骨架。学习者需要补全：

1. 列表接口使用 `select(Note)`，通过 `Note.user_id == current_user.id` 限定所有者，并按 `created_at`、`id` 倒序排列，返回查询到的全部结果。
2. 详情接口在同一条 SQL 查询中同时限定 `Note.id == note_id` 和 `Note.user_id == current_user.id`。

列表查询可以使用 `db.scalars(statement).all()`，详情查询可以使用 `db.scalar(statement)`。把用户条件放进 SQL 能让数据库只返回有权访问的数据；不要先按 ID 读取再在 Python 中检查所有者。

## 11. 复习问题与参考答案

1. **为什么 `notes` 表必须有 `user_id`？** 它记录每篇笔记的所有者，是建立用户与笔记一对多关系以及实施数据隔离的基础。
2. **为什么不能让创建请求提交 `user_id`？** 请求者可以伪造该值。所有者必须来自服务器已经验证的 `current_user.id`。
3. **为什么详情查询同时限制 `id` 和 `user_id`？** 数据库只会返回当前用户有权访问的目标记录，避免先取出他人数据再在应用层判断。
4. **为什么他人的笔记和不存在的笔记都返回 `404`？** 这样不会向请求者泄露某个资源 ID 是否真实存在。
5. **为什么空列表返回 `200 []` 而不是 `404`？** 列表资源存在，只是当前筛选条件下没有成员；这不是某个具体资源不存在。
6. **`db.commit()` 和 `db.refresh(note)` 各做什么？** `commit()` 提交事务使写入生效；`refresh()` 从数据库重新读取该对象，取得主键和数据库默认时间等值。
7. **请求模型和响应模型为什么分开？** 请求模型限制客户端可以提交的字段，响应模型限制服务端公开的字段，两者的数据边界不同。

小练习已完成：在笔记 `APIRouter` 上统一补充 `401` OpenAPI 响应说明。

## 14. 完整教程

本课先把产品中的“笔记属于用户”落实为数据库关系：`notes.user_id` 外键引用 `users.id`，并为按用户查询建立索引。模型还保存标题、长文本正文、创建时间和更新时间。Alembic 根据模型生成迁移，经检查后应用到 PostgreSQL。

接口层使用两个 Pydantic 模型建立边界。`NoteCreate` 只接受标题和正文，清除首尾空白并校验长度；`NotePublic` 只公开笔记自身信息。`user_id` 不进入请求体，而是由 Bearer Token 经 `get_current_user` 验证后得到。

创建接口把 `current_user.id` 写入新笔记，提交并刷新后返回。列表接口在 SQL 中使用当前用户 ID 过滤，并按创建时间和主键倒序排列；没有笔记时返回空数组。详情接口在同一条 SQL 中同时限制笔记 ID 和用户 ID，未找到时统一返回 `404`，因此既实现数据隔离，也避免泄露他人的资源是否存在。

最后通过两名真实用户完成 HTTP 验收：用户 A 可以创建和读取自己的笔记，用户 B 看不到用户 A 的笔记并在访问其 ID 时得到 `404`，未认证请求得到 `401`。路由器级 OpenAPI 配置同步记录了所有笔记接口共有的认证失败响应。
