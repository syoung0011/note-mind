## 1. 本课目标与边界

本课补全笔记后端的写操作，让已登录用户能够编辑和删除自己的笔记，同时继续保证用户之间的数据隔离。

本课接口范围：

```text
PUT    /api/notes/{id}  编辑当前用户的一篇笔记
DELETE /api/notes/{id}  删除当前用户的一篇笔记
```

本课不实现前端笔记页面、局部更新 `PATCH`、回收站、软删除、批量删除和操作审计；这些内容不扩大当前课程范围。

完成后应当能够解释：

- 更新请求模型为什么应与响应模型分开。
- 更新或删除时为什么仍需同时限制笔记 `id` 和当前用户 `user_id`。
- `PUT`、`DELETE` 的成功状态码和响应体如何设计。
- SQLAlchemy 会话中的查询、修改、删除和提交分别发生了什么。
- 为什么浏览器跨域请求还需要允许 `PUT` 和 `DELETE` 方法。

## 2. 核心流程

```text
Bearer Token
  → get_current_user 验证身份
  → 使用 note_id + current_user.id 查询目标笔记
  → 不存在或不属于当前用户：统一返回 404
  → 更新字段并提交，或删除记录并提交
  → 返回更新后的笔记，或返回无响应体的 204
```

权限边界延续第 8 课的原则：数据库查询本身就必须包含当前用户条件，不能先只按笔记 ID 取出记录，再在 Python 中判断所有者。

## 5. 检查点 A：接口契约与安全边界

建议采用下面的接口契约：

- `PUT /api/notes/{id}`：请求体包含完整的 `title` 和 `content`；成功返回 `200` 及更新后的 `NotePublic`。
- `DELETE /api/notes/{id}`：成功删除后返回 `204 No Content`，响应体为空。
- 两个接口在笔记不存在或属于其他用户时，都返回 `404 Note not found`。
- 未携带有效 Bearer Token 时返回 `401`；请求字段不合法时返回 `422`。

这里选择 `PUT`，表示客户端提交一份完整的可编辑内容来替换笔记当前内容；暂不引入允许只传一个字段的 `PATCH`，避免同时学习两套更新语义。

删除采用硬删除：提交事务后记录直接从 `notes` 表移除。回收站和软删除属于 MVP 之外的功能。

开始编码前，请先用自己的话思考两个问题：

1. 为什么编辑和删除都不能只使用 `Note.id == note_id` 查询？
2. 为什么删除成功适合返回 `204`，并且不能再携带 JSON 响应体？

不需要书面提交答案；回复“继续”即可进入检查点 B，届时会先给出参考答案和易错点，再建立可填写的更新模型骨架。

参考答案：编辑和删除必须同时使用笔记 ID 与当前用户 ID 查询，使数据库只返回当前用户有权操作的目标；如果只按笔记 ID 查询，就可能读取或修改其他用户的数据。`204 No Content` 明确表示响应没有内容，因此删除成功后不能再携带 JSON 响应体。


### 复习问题与参考答案

1. **为什么更新和删除都要使用 `note_id + current_user.id` 查询？** 数据库只返回当前用户有权操作的目标，避免越权，也能把不存在和无权访问统一隐藏为 `404`。
2. **为什么更新后要提交并刷新？** `commit()` 把修改写入数据库；`refresh(note)` 重新读取数据库结果，包括更新后的时间等字段。
3. **为什么删除后不刷新？** 提交后记录已经不存在，无法再从数据库刷新。
4. **为什么 `204` 不返回 JSON？** `204 No Content` 的协议语义就是响应没有内容。
5. **为什么请求模型不能直接使用 ORM 模型？** 请求 Schema 控制客户端允许提交的字段，ORM 模型描述数据库记录，两者承担不同的数据边界。
6. **为什么还要修改 CORS？** 浏览器跨域发送 `PUT`、`DELETE` 前会检查服务端是否允许这些方法；只有路由存在并不足以通过浏览器的跨域限制。

易错点：请求值来自 `note_in` 实例而不是 `NoteUpdate` 类；`db.refresh()` 必须传入对象；修改 ORM 查询对象不需要再次 `db.add()`；成功返回 `204` 时不能附带内容。

完成小修改并在 Swagger UI 中确认后回复“确认”，AI 会审阅最终差异并给出由你亲自执行的 Git 提交命令。

学习者加入了指定文本，但初次把 `response_description` 写进 `delete_note()` 的函数参数。这样 FastAPI 会把它解释为接口的可选查询参数，而不是路由元数据。AI 已将它移动到 `@router.delete(...)` 装饰器中，使 OpenAPI 的 `204` 成功响应描述正确更新，同时不改变接口运行行为。

易错点：路由配置项属于装饰器；路径参数、请求数据和依赖项才属于路由函数签名。代码能够通过 Python 语法检查，不代表框架会按照预期解释参数。

## 13. 完整教程

本课先为完整更新建立独立的 `NoteUpdate` 请求模型。虽然它目前和创建模型拥有相同字段，但单独定义能够保持创建与更新的接口边界，避免未来规则变化时互相影响。`PUT` 要求客户端提交完整的标题和正文，Pydantic 在路由执行前负责去除首尾空白并验证长度。

编辑和删除都先通过 `get_current_user` 获得已验证用户，再在同一条 SQL 查询中同时限制笔记 ID 和用户 ID。这让数据库只返回当前用户有权操作的记录；目标不存在或属于其他用户时统一返回 `404`，避免泄露资源是否存在。

编辑时修改当前会话已经管理的 ORM 对象，不需要再次 `db.add()`。`db.commit()` 把 `UPDATE` 写入数据库，`db.refresh(note)` 重新读取数据库值，然后由 `NotePublic` 序列化为 `200` 响应。删除时使用 `db.delete(note)` 标记记录并提交事务；记录已经不存在，因此不刷新、不返回对象，接口以空响应体的 `204` 表示成功。

最后在 CORS 中允许 `PUT` 与 `DELETE`，使后续 Vue 前端的跨域预检能够通过。双用户实际验收覆盖了正常更新、参数错误、越权更新与删除、正常删除、删除后查询和未授权访问。
